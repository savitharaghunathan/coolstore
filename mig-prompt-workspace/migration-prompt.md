## Current Application Summary

CoolStore is a retail storefront monolith originally built as a Java EE 7 application deployed on JBoss EAP 7.4 in a clustered (standalone-full-ha) configuration. The application serves an AngularJS front end (served from `src/main/webapp` with vendored bower assets), exposes JAX-RS REST endpoints for catalog, cart, product, and order operations, persists JPA entities to PostgreSQL, secures checkout via Keycloak OIDC, and processes orders asynchronously through a JMS topic (`topic/orders`) consumed by Message-Driven Beans. The source platform relies on EJB 3.2 (`@Stateless`, `@Stateful`, `@MessageDriven`), JPA 2.1 (Hibernate), and container-managed transactions.

A prior in-house translation effort (documented in `migration/MIGRATION-COMPLETE.md`) already converted the majority of the codebase to Quarkus 3.8.1: `pom.xml` now targets the Quarkus BOM 3.8.1, all 21 scanned main-source files use `jakarta.*` imports (0 `javax.*` remain), and `application.properties` carries Quarkus datasource, Hibernate, Kafka-backed SmallRye Reactive Messaging, and OIDC configuration. However, the migration is **incomplete and not production-hardened**: Java EE remnants remain (WebLogic compatibility shim classes under `src/main/java/weblogic/application/`, a legacy `web.xml`, a `javax.persistence`-configured test `persistence.xml`, and messaging conversion gaps in `InventoryNotificationMDB`), and three `[TODO(port)]` items are tracked in the build: production PostgreSQL datasource, Keycloak realm/client wiring, and the custom `audit-logging-library` (jars in `lib/` not yet resolvable from Maven).

## Migration Approach

**Strategy:** Phased completion and hardening of the in-flight migration (hybrid: finish remaining translation, then validate, containerize, and deploy).

**Reasoning:**
- The bulk translation is already done and compiles (per `migration/MIGRATION-COMPLETE.md` and build logs: 47 → 0 compile errors), so a big-bang restart would discard validated work
- Remaining risk concentrates in: messaging parity (JMS transactions → Kafka + `@Transactional` semantics), unresolved production configuration (PostgreSQL, Keycloak, audit library), leftover Java EE artifacts, and unverified behavior parity
- Phased completion lets each risk be retired behind a gate (compile → smoke → parity → container → cluster)

**Phases:**
1. **Foundation & Cleanup** — remove WebLogic shims and legacy descriptors, close messaging conversion gaps, resolve `audit-logging-library`, align tests with Quarkus test tooling
2. **Configuration & Integrations** — production PostgreSQL profile, Kafka topic/DLQ provisioning, Keycloak realm/client wiring, secrets externalization
3. **Validation & Parity** — smoke tests, characterization/unit/integration test execution, behavior parity vs. the Java EE baseline
4. **Containerization** — multi-stage Containerfile, image scanning, registry publication
5. **OpenShift Deployment** — manifests, probes, autoscaling, GitOps pipeline, cutover and rollback drill

**Key Considerations:**
- **Transactions**: EJB MDBs ran container-managed transactions; SmallRye `@Incoming` methods do not — every consumer performing JPA writes MUST be `@Transactional` (jakarta.transaction). Audit `InventoryNotificationMDB` and `OrderServiceMDB` for this.
- **Messaging semantics**: JMS topic → Kafka topic changes delivery semantics (consumer groups vs. shared subscriptions); configure `auto.offset.reset=earliest`, idempotent producers (`acks=all`, `enable.idempotence=true`), and dead-letter-queue failure strategy (already drafted in `application.properties`).
- **Stateful EJB**: `ShoppingCartService` (`@Stateful`) must become `@SessionScoped` or be refactored stateless — verify cart behavior end-to-end.
- **Schema management**: keep Flyway migrations (`V1_1`, `V1_2`) as source of truth; `validate` (not `update`) in production profiles.
- **Front end**: AngularJS assets are served as static resources — no rewrite in scope; must remain reachable under the Quarkus jar packaging.
- **Data migration**: retain the existing PostgreSQL database; Flyway migrations are already idempotent from the source system.

## Constraints and Risks

**Constraints:**
- Preserve existing REST API contracts and JSON payloads (front end depends on them)
- Keep the AngularJS front end and bower assets as static resources (no front-end rewrite)
- Java 11 toolchain per current `pom.xml` (verify Quarkus 3.8.1 compatibility; bump to 17 only if required)
- Database remains PostgreSQL; no data-model redesign
- Repository carries a read-only rulebook: translation decisions must cite `migration/RULEBOOK.md` rather than invent new patterns

**Risks:**
- **Transaction semantics drift** (HIGH): `@Incoming` consumers without `@Transactional` will fail at runtime with `TransactionRequiredException` — must be verified on every consumer, not just at compile time
- **Kafka vs. JMS delivery semantics** (HIGH): duplicated or missed orders during cutover; mitigate with idempotent producers, `auto.offset.reset=earliest`, DLQ strategy, and a parallel-run window
- **Stateful cart behavior** (MEDIUM): `@Stateful` → CDI scope conversion can break multi-request cart flows; cover with characterization tests
- **Unresolved custom library** (MEDIUM): `audit-logging-library` jars not in any Maven repository; requires `mvn install:install-file` bootstrap, internal repo publication, or feature-gap decision
- **Keycloak realm migration** (MEDIUM): realm `eap` export exists (`realm-export.json`) but client secrets/redirect URIs must be re-wired for OpenShift routes
