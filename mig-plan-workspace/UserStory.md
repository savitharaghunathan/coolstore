## User Story 1: Clean, Legacy-Free Quarkus Codebase

**As a:** Developer on the CoolStore team
**I want:** The Quarkus 3.8.1 codebase with all WebLogic/Java EE remnants removed and the model/utils layers hardened
**So that:** The application is a pure Jakarta/Quarkus codebase that compiles cleanly, has no dead compatibility shims, and is safe to build on

---

### Tasks
- ## Task Group 1: Baseline Verification & Java EE Remnant Cleanup
- ## Task Group 2: Model & Utils Layer Hardening (com.redhat.coolstore.model, .utils)

### Acceptance Criteria
- [ ] `mvn clean verify` passes on a clean checkout (recorded baseline)
- [ ] `weblogic/application/*` classes, legacy `web.xml`, and javax-persistence test `persistence.xml` are deleted; app boots without them
- [ ] `grep -rn "javax\.\|weblogic\|jboss" src/` returns only annotated comments
- [ ] All 8 model classes verified against the Flyway schema; Transformers JSON round-trips byte-identical
- [ ] Startup path (Flyway migration + lifecycle events) works under Quarkus

### Details
- **Priority:** High — everything else depends on a clean base
- **Estimate:** 5 story points

### Preconditions
- Repository access; Maven + JDK 11 toolchain; rgctl index available (`.rgctl/`)

### Steps to Reproduce / Implementation Notes
1. Run baseline build; delete remnants per TG 1.2–1.4
2. Audit model/utils per TG 2.1–2.4 citing `migration/RULEBOOK.md` rules
3. Validate via unit tests and a dev-mode boot

### Dependencies
- None (first story)

### Test Cases
- Test 1: App startup with Flyway `V1_1`/`V1_2` applied — expected: no schema errors
- Test 2: `Transformers.shoppingCartToJson`/`jsonToOrder` round-trip — expected: byte-identical payloads
- Test 3: Model persistence smoke (persist/load each entity) — expected: JPA mappings correct

### Notes / Comments
- rgctl package order puts `model` and `utils` first (steps 5–6 of `migration_plan.json`) — this story matches that order
- Update `migration/inventory.tsv` statuses as files are verified

## User Story 2: Reliable Asynchronous Order Pipeline

**As a:** Store operations owner
**I want:** Checkout orders flowing through Kafka with transactional consumers and a dead-letter queue
**So that:** Every order is persisted and inventory updated exactly once, with failures quarantined instead of silently lost

---

### Tasks
- ## Task Group 3: Service Layer Completion — Messaging & Transactions (com.redhat.coolstore.service)

### Acceptance Criteria
- [ ] Every `@Incoming` consumer method performing JPA writes is annotated `@Transactional` (RULEBOOK Amendment 1)
- [ ] `ShoppingCartOrderProcessor` emits to Kafka `orders` topic with `acks=all` + idempotence enabled
- [ ] Poison messages land in `orders-dlq`; consumer group `coolstore-orders` replays correctly after restart
- [ ] `ShippingServiceRemote` decision executed (delete + de-implement, after rgctl blast-radius confirms no consumers)
- [ ] `ShoppingCartService` `@SessionScoped` cart survives multi-request flows and passivation
- [ ] Pricing/promotion/shipping behavior matches Java EE baseline

### Details
- **Priority:** High — highest runtime risk in the migration (transaction semantics)
- **Estimate:** 8 story points

### Preconditions
- User Story 1 complete (models/transformers verified)
- Kafka available in dev (Quarkus dev services or local broker)

### Steps to Reproduce / Implementation Notes
1. Transaction audit first (TG 3.1) — this failure mode is invisible to the compiler
2. Verify channel/DLQ configuration in `application.properties` against actual consumer code
3. Run Kafka round-trip and poison-message tests before touching anything else

### Dependencies
- User Story 1

### Test Cases
- Test 1: Checkout → order JSON on `orders` topic → `OrderServiceMDB` persists, inventory decremented — expected: atomic
- Test 2: Malformed message → routed to `orders-dlq`, consumer stays alive — expected: no crash, no loss
- Test 3: Restart consumer mid-stream → messages resume from committed offset — expected: no duplicates/loss
- Test 4: Cart with promotions/shipping recalculates identically to baseline values

### Notes / Comments
- JMS topic (shared subscriptions) → Kafka (consumer groups) semantic shift is the core risk; DLQ strategy already drafted in `application.properties`
- Keep JBoss EAP instance available during parallel-run for comparison (see Story 6)

## User Story 3: Modern Web Experience with API Parity

**As a:** CoolStore shopper
**I want:** The AngularJS storefront served by the Quarkus app with identical REST contracts
**So that:** Browsing, cart, and checkout work exactly as before the migration with no visible change

---

### Tasks
- ## Task Group 4: REST Layer & Static Front End (com.redhat.coolstore.rest)

### Acceptance Criteria
- [ ] All REST endpoints (`/cart`, `/products`, `/orders`, etc.) respond with identical routes, status codes, and JSON shapes as the Java EE baseline
- [ ] AngularJS assets (`src/main/webapp/**`) served statically from the Quarkus jar; `health.jsp` replaced by `q/health`
- [ ] Front-end Keycloak adapter (`keycloak.json`) consistent with realm wiring from User Story 4
- [ ] RESTEasy Reactive/Jackson serialization matches legacy JAX-RS output

### Details
- **Priority:** High — user-visible surface
- **Estimate:** 5 story points

### Preconditions
- User Story 2 complete (endpoints can transact)
- API contract freeze list captured from baseline

### Steps to Reproduce / Implementation Notes
1. Capture baseline API responses from the JBoss EAP instance (characterization)
2. Serve static front end; compare Quarkus responses field-by-field
3. Manual checkout walkthrough against dev stack

### Dependencies
- User Story 2 (service behavior behind endpoints)

### Test Cases
- Test 1: `@QuarkusTest` contract suite per endpoint — expected: payload-shape parity vs. baseline captures
- Test 2: Front-end index + bower assets load from `/` — expected: 200s, app renders
- Test 3: Health endpoint `q/health/ready` — expected: UP when DB/Kafka connected

### Notes / Comments
- No front-end rewrite in scope — assets move as static resources
- Vendored bower assets dominate the rgctl graph; exclude from future indexing to keep analysis signal clean

## User Story 4: Production-Ready, Secure Configuration

**As a:** Platform engineer
**I want:** Production PostgreSQL, Keycloak OIDC, Kafka, and the audit library wired via externalized secrets
**So that:** The application runs securely in production without hardcoded credentials or dev-grade databases

---

### Tasks
- ## Task Group 5: Production Configuration, Security & Integrations

### Acceptance Criteria
- [ ] `%prod` profile uses PostgreSQL with `database.generation=validate`; Flyway is the schema authority
- [ ] `audit-logging-library` resolved (install-file or internal repo), dependency uncommented, version decision recorded
- [ ] Keycloak realm `eap` imported, `coolstore` client wired (`quarkus.oidc.*`), front-end redirect URIs updated
- [ ] All 7 rgctl secret findings triaged; DB/Kafka/OIDC credentials sourced from OpenShift Secrets
- [ ] Profile matrix (`%dev`/`%test`/`%prod`) documented and verified

### Details
- **Priority:** High — blocks production deployment
- **Estimate:** 8 story points

### Preconditions
- User Story 1 complete
- Target Keycloak and PostgreSQL instances reachable (or dev-services equivalents)

### Steps to Reproduce / Implementation Notes
1. PostgreSQL profile first (clears the biggest TODO(port))
2. Audit library resolution (2.0.0 jar preferred; verify compatibility)
3. Keycloak import from `realm-export.json` + client secret rotation into a Secret
4. Secret sweep: move every credential to env/Secret

### Dependencies
- User Story 1; User Story 3 (front-end keycloak.json alignment)

### Test Cases
- Test 1: OIDC flow — unauthenticated checkout call → 401; valid token → 200
- Test 2: `%prod` profile boot against PostgreSQL — expected: schema validates, app healthy
- Test 3: No plaintext credentials in image or source (secret scan clean)

### Notes / Comments
- The 7 security findings and 1 taint flow (vendored `gulpfile.js`, out of app scope) come from the rgctl `--with-security`/`--with-taint` discover
- Document each secret finding disposition — required for the CVE/secret gate in Story 6

## User Story 6: Containerized Deployment on OpenShift

**As a:** Platform engineer
**I want:** The verified Quarkus application containerized, scanned, and deployed to OpenShift with health probes, autoscaling, and a rollback plan
**So that:** CoolStore runs as a cloud-native workload with operational safety and no downtime cutover

---

### Tasks
- ## Task Group 7: Containerization
- ## Task Group 8: OpenShift Deployment & Cutover

### Acceptance Criteria
- [ ] Multi-stage Containerfile builds a non-root image; CVE scan passes; image pushed to OpenShift registry
- [ ] Native-image decision recorded (build or justified JVM fallback)
- [ ] OpenShift manifests: Deployment (limits/HPA), Service, Route, ConfigMaps, Secret refs, `q/health` probes
- [ ] PostgreSQL, Kafka (`orders`, `orders-dlq`), Keycloak provisioned on-cluster or bound externally
- [ ] Tekton pipeline: build → test → scan → deploy; GitOps promotion
- [ ] Parallel-run window against JBoss EAP verified; documented rollback (EAP redeploy + Kafka offset rewind)
- [ ] Observability: Prometheus metrics, JSON logs, DLQ-depth alerting

### Details
- **Priority:** High — final delivery
- **Estimate:** 13 story points

### Preconditions
- User Story 5 complete (green suite — hard gate)
- OpenShift cluster access with registry and AMQ Streams

### Steps to Reproduce / Implementation Notes
1. Build + scan image (TG 7); evaluate native build
2. Author manifests and provision backing services (TG 8.1–8.2)
3. Wire pipeline and deploy to staging; run post-deploy smoke suite
4. Execute cutover with parallel-run; monitor DLQ and health for the soak window

### Dependencies
- User Stories 1–5

### Test Cases
- Test 1: Container starts and passes health checks within N seconds — expected: ready probe green
- Test 2: Post-deploy smoke suite on cluster — expected: all green
- Test 3: Rollback drill in staging — expected: EAP redeploy restores service within RTO

### Notes / Comments
- Image must contain no secrets — all config from ConfigMaps/Secrets (Story 4 inventory)
- Keep JBoss EAP warm for the agreed rollback window (30 days recommended)
