## User Story 1: Verified Green Baseline

**As a:** Migration Engineer
**I want:** The Quarkus-migrated codebase to build and pass its full test suite locally
**So that:** Every subsequent migration change is measured against a known-good baseline instead of compounding unknown breakage

---

### Tasks
- ## Task Group 1: Baseline Verification & Test Suite Restoration

### Acceptance Criteria
- [ ] `mvn clean verify` completes with zero compilation errors and all tests passing
- [ ] `ShoppingCartOrderProcessorTest` tests the SmallRye `@Channel`/`Emitter` contract (no `javax.jms` imports)
- [ ] `mockito-junit-jupiter` present in `pom.xml` test scope
- [ ] `@Transactional` verified present on `OrderServiceMDB` and `InventoryNotificationMDB` `@Incoming` methods
- [ ] The 18 deferred port markers are triaged with owners and dispositions recorded

### Details
- **Priority:** High — blocks all other stories
- **Estimate:** 3 story points (small suite: 23 test classes, ~1.8K test LOC; one legacy-import rewrite)

### Preconditions
- Java 11+ and Maven available; repo on branch `konveyor/migration-1793137290`
- H2 in-memory + in-memory Kafka connector profiles (`%test`) functional

### Steps to Reproduce / Implementation Notes
1. Rewrite `ShoppingCartOrderProcessorTest` per TG1.1; add test dependency per TG1.2
2. Run `mvn clean verify`, burn down failures (TG1.3)
3. Verify transaction annotations and triage markers (TG1.4–1.5)
4. Generate characterization tests for pricing/order logic via mig-test-gen (TG1.6)

### Dependencies
- None — first story

### Test Cases
- Test 1: Cart pricing unit tests (totals, promotion, shipping) — parity with Java EE reference values
- Test 2: Order producer test — `process(cart)` emits JSON on `orders` channel
- Test 3: Full `mvn verify` — green

### Notes / Comments
- The prior kit run verified compile-only (47 → 0 errors); test restoration is explicitly
  listed as its "Immediate next step". This story closes that gap.

## User Story 3: Frontend Served by Quarkus

**As a:** Storefront User
**I want:** The CoolStore AngularJS web UI and health checks served directly by the Quarkus application
**So that:** The single Quarkus jar delivers the complete storefront experience without JBoss/JSP infrastructure

---

### Tasks
- ## Task Group 3: Frontend Static Serving Migration

### Acceptance Criteria
- [ ] `quarkus-smallrye-health` extension in `pom.xml`; `/q/health/live` and `/q/health/ready` return 200
- [ ] Webapp assets served from `META-INF/resources/` with original absolute paths intact
- [ ] `index.html` (converted from `index.jsp`) loads the app; no JSPs remain
- [ ] REST base path decision (`/services` vs Quarkus default) made and frontend config aligned
- [ ] Static smoke tests committed

### Details
- **Priority:** High
- **Estimate:** 3 story points (asset move is mechanical; base-path and session semantics need care)

### Preconditions
- User Story 2 complete (no WAR packaging leftovers)
- Frontend asset inventory understood (`app/`, `partials/`, `bower_components/`, JSON configs)

### Steps to Reproduce / Implementation Notes
1. Add health extension (TG3.1); move assets preserving paths (TG3.2)
2. Convert `index.jsp` → `index.html`, dropping the session scriptlet (TG3.3)
3. Replace `health.jsp` with health endpoints (TG3.4); resolve base-path TODO (TG3.5)
4. Generate static/health smoke tests via mig-test-gen (TG3.6)

### Dependencies
- User Story 2

### Test Cases
- Test 1: `GET /` → 200 and HTML references loadable assets
- Test 2: `GET /bower_components/jquery/dist/jquery.min.js` → 200
- Test 3: `GET /q/health/live` → 200; `/q/health/ready` reflects dependency state

### Notes / Comments
- Quarkus jars do not serve JSPs — this is a hard requirement for leaving JBoss EAP.
- ~1,200 frontend files (mostly vendored bower libs) move verbatim; no frontend rewrite.

## User Story 4: Secured Checkout with Keycloak OIDC

**As a:** Storefront Customer
**I want:** Cart and order operations protected by Keycloak authentication while catalog browsing stays public
**So that:** My shopping session is secure and only I can check out and view my orders, matching the original application's behavior

---

### Tasks
- ## Task Group 4: Security Port — Keycloak OIDC

### Acceptance Criteria
- [ ] `ProductEndpoint` is `@PermitAll`; `CartEndpoint` and `OrderEndpoint` enforce the realm role
- [ ] OIDC configuration active in `application.properties` (no placeholder TODO block)
- [ ] Unauthenticated checkout returns 401; wrong-role access returns 403
- [ ] CORS configured for the frontend origin; `keycloak.json` points at the environment Keycloak
- [ ] Security tests committed and green

### Details
- **Priority:** High — security gap blocks any external exposure
- **Estimate:** 5 story points (annotation + config work is moderate; test setup with OIDC is the effort)

### Preconditions
- User Story 3 complete (frontend served, base path settled)
- Keycloak realm `eap` export available (`realm-export.json`); role names verified

### Steps to Reproduce / Implementation Notes
1. Annotate endpoints per original semantics (TG4.1)
2. Activate OIDC properties and dev-mode escape hatch (TG4.2–4.3)
3. Configure CORS (TG4.4); confirm dependency state (TG4.5)
4. Generate security tests via mig-test-gen (TG4.6)

### Dependencies
- User Story 3
- Keycloak instance reachable in test environment

### Test Cases
- Test 1: `GET /services/products` without token → 200
- Test 2: `POST /services/cart/checkout/{cartId}` without token → 401
- Test 3: Valid token with realm role → checkout 200, order persisted
- Test 4: Token without role → 403

### Notes / Comments
- Currently zero security annotations exist on endpoints — the entire security model
  must be re-established; this is the highest-severity risk in the migration prompt.

## User Story 5: Production-Ready Data Layer

**As a:** Operations Engineer
**I want:** The application running against production PostgreSQL with Flyway-managed schema and no secrets in Git
**So that:** Data is durable, schema changes are controlled, and credentials meet security policy

---

### Tasks
- ## Task Group 5: Data & Configuration Hardening — Production PostgreSQL

### Acceptance Criteria
- [ ] `%prod` PostgreSQL datasource configured via env vars; H2 confined to `%dev`/`%test`
- [ ] Flyway migrations validated against real PostgreSQL (Testcontainers) and pass
- [ ] Hibernate generation mode per profile: `update`/dev, `drop-and-create`/test, `validate`/prod
- [ ] All 7 rgctl-flagged potential secrets removed from the repo and externalized
- [ ] CI secret-scanning step active

### Details
- **Priority:** High
- **Estimate:** 5 story points (config moderate; PostgreSQL dialect validation and secret scrub need diligence)

### Preconditions
- User Story 1 complete (green suite to extend)
- PostgreSQL available for integration testing (Testcontainers acceptable)

### Steps to Reproduce / Implementation Notes
1. Implement `%prod` datasource block (TG5.1)
2. Validate Flyway SQL on PostgreSQL; reconcile `DataBaseMigrationStartup` vs
   `quarkus.flyway.migrate-at-start` (TG5.2–5.3)
3. Scrub and externalize secrets; add CI scanning (TG5.4)
4. Generate persistence integration tests via mig-test-gen (TG5.5)

### Dependencies
- User Story 1 (parallel with Stories 3–4 after gate)
- PostgreSQL service for integration tests

### Test Cases
- Test 1: Testcontainers-PostgreSQL — Flyway migrates cleanly, catalog query returns seeded data
- Test 2: Order persists and is retrievable by ID on PostgreSQL
- Test 3: Secret scan of repo — zero findings

### Notes / Comments
- Migrations were authored under H2; PostgreSQL-specific dialect issues are likely
  and must surface in tests, not in production.

## User Story 6: Container Image

**As a:** DevOps Engineer
**I want:** A hardened, scanned OCI image of the CoolStore Quarkus app built by a repeatable pipeline
**So that:** The application can be deployed consistently to any OpenShift environment

---

### Tasks
- ## Task Group 6: Containerization

### Acceptance Criteria
- [ ] Multi-stage `Containerfile` builds from source; fast-jar runtime on a minimal base image
- [ ] Container runs as non-root with container-aware JVM flags
- [ ] Image tagged by git SHA; pushed to OpenShift internal registry
- [ ] Image scan shows no critical vulnerabilities (or documented exceptions)
- [ ] Runtime env contract (`QUARKUS_OIDC_*`, `QUARKUS_DATASOURCE_*`, Kafka bootstrap) validated

### Details
- **Priority:** Medium
- **Estimate:** 3 story points (single small service; standard Quarkus image pattern)

### Preconditions
- User Stories 3, 4, 5 complete (image content and env contract final)
- Podman/buildah available; OpenShift registry credentials

### Steps to Reproduce / Implementation Notes
1. Author multi-stage Containerfile (TG6.1–6.2)
2. Establish tagging/promotion and scanning (TG6.3–6.4)
3. Wire env contract incl. overriding the hardcoded Kafka bootstrap default (TG6.5)
4. Generate container smoke tests via mig-test-gen; run mig-containerize (TG6.6–6.7)

### Dependencies
- User Stories 3, 4, 5

### Test Cases
- Test 1: `podman build` succeeds from clean checkout
- Test 2: Container starts; `/q/health/live` → 200 within 60s
- Test 3: Readiness fails (not liveness) when DB/Kafka unavailable
- Test 4: Image scan — zero criticals

### Notes / Comments
- JVM mode recommended for this phase; native image is a documented follow-up.
- Kafka bootstrap is currently a hardcoded default in `application.properties` —
  must be env-overridable for OpenShift.

## User Story 7: Running on OpenShift

**As a:** Platform Owner
**I want:** CoolStore deployed to OpenShift with Keycloak, Kafka, and PostgreSQL wired via manifests and CI/CD
**So that:** The storefront runs on supported cloud infrastructure with health-managed, autoscaled, secret-driven operations

---

### Tasks
- ## Task Group 7: OpenShift Deployment

### Acceptance Criteria
- [ ] Deployment (2 replicas), Service, Route, ConfigMap, Secrets, ServiceAccount committed under `k8s/`
- [ ] Liveness/readiness probes wired to `/q/health/*`; rolling updates with zero-downtime config
- [ ] Kafka topics `orders`, `orders-dlq`, `inventory-dlq` provisioned; both consumer groups active
- [ ] Keycloak realm `eap` + client `eap-app` provisioned; app authenticates end-to-end
- [ ] PostgreSQL provisioned with Flyway-run schema; resource limits and HPA configured
- [ ] Tekton pipeline builds and deploys from Git

### Details
- **Priority:** Medium
- **Estimate:** 8 story points (most integration-heavy story: four moving parts across infra)

### Preconditions
- User Story 6 complete (image in registry)
- OpenShift 4.x project with AMQ Streams, Keycloak Operator, PostgreSQL available

### Steps to Reproduce / Implementation Notes
1. Author manifests with probes and resource policy (TG7.1–7.2, 7.6)
2. Provision Kafka/Keycloak/PostgreSQL dependencies (TG7.3–7.5)
3. Stand up Tekton pipeline including secret scanning (TG7.7)
4. Generate post-deploy smoke suite via mig-test-gen; run mig-deploy (TG7.8–7.9)

### Dependencies
- User Story 6
- Cluster operators: AMQ Streams, Keycloak, database

### Test Cases
- Test 1: Route serves storefront; health probes pass on both replicas
- Test 2: Signed-in checkout via Keycloak → order persisted → both consumers process
- Test 3: Pod kill during traffic — rolling update with no failed user requests
- Test 4: Pipeline from commit → image → deploy succeeds

### Notes / Comments
- Kafka consumer-group mapping (two groups on one topic) is the semantic replacement
  for the JMS topic broadcast; document it next to the manifests.

## User Story 8: Parity Sign-Off & Observability

**As a:** Product Owner
**I want:** Proof that the Quarkus application matches Java EE behavior, with monitoring in place and the legacy deployment decommissioned
**So that:** I can confidently retire the JBoss EAP stack and operate the new platform going forward

---

### Tasks
- ## Task Group 8: Validation, Parity & Observability

### Acceptance Criteria
- [ ] E2E parity suite green: catalog → cart → authenticated checkout → order persisted → inventory processed
- [ ] DLQ failure strategy demonstrated with a poison message; no message loss on consumer restart
- [ ] Performance baseline recorded (startup, memory, checkout latency) vs. JBoss EAP reference
- [ ] Micrometer/Prometheus metrics and JSON logs flowing to cluster observability stack
- [ ] Must-fix marker burn-down complete; remaining markers re-tagged post-launch
- [ ] Final image re-scanned clean; JBoss deployment path decommissioned with 30-day rollback documented

### Details
- **Priority:** Medium
- **Estimate:** 5 story points (suite execution and analysis; infra mostly from Story 7)

### Preconditions
- User Story 7 complete (app live on OpenShift with dependencies)
- Java EE reference behavior captured (characterization baseline from Story 1)

### Steps to Reproduce / Implementation Notes
1. Execute E2E parity and messaging resilience suites (TG8.1–8.2)
2. Record performance baseline and observability wiring (TG8.3–8.4)
3. Burn down triaged markers; final scans; cutover sign-off (TG8.5–8.8)
4. Deliver completion report and team training (TG8.9)

### Dependencies
- User Story 7

### Test Cases
- Test 1: E2E checkout parity — order value, discounts, shipping match Java EE reference
- Test 2: Poison message → `orders-dlq`; healthy messages unaffected
- Test 3: Consumer restart — offset replay resumes without loss
- Test 4: Grafana/Prometheus shows app metrics; dashboards saved

### Notes / Comments
- Keep the JBoss EAP rollback path documented for 30 days post-cutover, then remove.
- Success criteria for the whole migration (migration prompt) are verified here.
